PR 标题
fix(client): 在关闭 worker 池时保持解码到路由的消息顺序一致

关联 Issue
Closes #392

摘要
本 PR 修复了客户端模式下使用自定义解码器且不启用 worker 池时的消息顺序问题。

在修复前，解码后的消息可能会以乱序进入路由处理器，因为在无 worker 池路径中，每个请求都会通过独立 goroutine 分发执行。

问题描述
在客户端模式（`newCliMsgHandle`）下，`WorkerPoolSize` 被设置为 `0`。
在 `MsgHandle.Intercept` 中，当 worker 池关闭时，消息处理使用了：
- `go mh.doMsgHandler(...)`
- `go mh.doMsgHandlerSlices(...)`

这会引入同一连接内请求之间的并发。如果前一条消息处理更慢，后一条消息可能先进入路由处理，导致“解码顺序 != 路由处理顺序”。

根因分析
无 worker 池分支始终采用异步 goroutine 分发，包括客户端模式；但客户端场景通常要求单连接内严格顺序处理。

改动内容
1) 为 `MsgHandle` 增加 `clientMode` 标记：
- `newMsgHandle()`（服务端）：`clientMode=false`
- `newCliMsgHandle()`（客户端）：`clientMode=true`

2) 调整 `MsgHandle.Intercept` 在无 worker 池（`WorkerPoolSize == 0`）下的行为：
- 客户端模式：改为同步执行路由，保证顺序
  - `mh.doMsgHandler(...)` / `mh.doMsgHandlerSlices(...)`
- 服务端模式：保持原有异步行为（兼容历史语义）
  - `go mh.doMsgHandler(...)` / `go mh.doMsgHandlerSlices(...)`

3) 增加回归测试：
- `TestClientMsgHandleNoWorkerPoolPreservesOrder`
  - 验证客户端模式保持 `[1,2]` 顺序
- `TestServerMsgHandleNoWorkerPoolRemainsAsync`
  - 验证服务端无 worker 池仍为异步（延迟首条消息时得到 `[2,1]`）

变更文件
- `znet/msghandler.go`
- `znet/msghandler_client_order_test.go`（新增）

修复后行为
- 客户端模式 + 自定义解码器 + 无 worker 池：
  - 路由执行顺序与解码输出顺序一致（同一连接）。
- 服务端无 worker 池路径：
  - 仍保持异步行为（向后兼容）。

测试方式
1) 运行定向回归测试：

`go -C /home/calelin/dev/zinx test ./znet -run 'TestClientMsgHandleNoWorkerPoolPreservesOrder|TestServerMsgHandleNoWorkerPoolRemainsAsync' -count=1`

2) 重复运行客户端顺序测试验证稳定性：

`go -C /home/calelin/dev/zinx test ./znet -run TestClientMsgHandleNoWorkerPoolPreservesOrder -count=10`

本地验证结果
1) 定向回归输出：

`ok  	github.com/aceld/zinx/znet	0.244s`

2) 重复顺序测试输出：

`ok  	github.com/aceld/zinx/znet	1.207s`

风险评估
低风险。
改动范围仅限无 worker 池分发分支，并且仅在客户端模式下改为同步执行以保证顺序正确性。
